# Review Console：多项目审查台

Status: ready-for-agent

功能范围来自交接及本轮确认。本文件是本地 issue tracker 中的规格原文；测试按下述默认边界执行，性能目标需在实现后实测。

## Problem Statement

用户在 macOS 的 Otty 中运行十几个 pi 会话，通常各自处理不同项目。每轮 Agent 工作结束后，用户需要阅读改动、理解最终回复，并随时打开相关文件查看上下文。用户主要审查代码，也会编辑 Markdown，偶尔修改代码。

目前本轮改动和渲染后的回复位于两个独立浏览器页面，查看文件又需要转到其他工具。用户需要自己记住“哪个项目、哪个会话、哪一轮”，在页面和终端之间反复切换。多个项目长期打开时，现有编辑器的资源占用也是负担。

目标不是另造完整 IDE 或 pi 聊天客户端，而是把审查所需的信息放在一个轻量、统一的窗口里，让“看回复 → 看改动 → 查文件 → 少量修改 → 继续追问”成为连续操作。

第一版包含文件编辑和 Git 历史。此前交接中把文件树、编辑和 Git 历史后置的 MVP 范围，已被用户本轮要求取代。

## Solution

提供一个独立 pi 插件及其共享本地服务，在一个浏览器页面内呈现四栏：

1. 项目：切换项目，查看会话工作状态及改动数量。
2. 文件：上部列出相关改动文件，下部按需展开项目文件树。
3. 内容：查看本轮快照改动、Git 历史、完整文件，并编辑当前磁盘文件。
4. 回复：阅读对应会话的回复，保留现有 visual-reply 的阅读、渲染和发送消息能力。

四栏可以折叠。项目、会话和轮次明确区分；本轮快照报告与该轮回复绑定。Git 历史独立浏览，不把提交 diff 当作 Agent 本轮报告。

界面布局参考已查看的 Paper 四张主画板。第一版优先实现信息结构和操作，不以最终配色、字体微调或视觉重设计为验收重点。

## User Stories

### 项目与会话

1. 作为多项目开发者，我希望在同一窗口切换十几个项目，以便不再到处寻找窗口或标签页。
2. 作为审查者，我希望添加和移除本地项目，以便维护自己的项目列表。
3. 作为审查者，我希望项目列表保留顺序，以便常用项目容易找到。
4. 作为审查者，我希望一个项目可以关联多个会话，以便不会把同仓库内的不同任务混在一起。
5. 作为审查者，我希望选择具体会话，以便知道当前回复和报告来自哪个任务。
6. 作为审查者，我希望工作状态与改动数量独立显示，以便不会把“仍在运行”误认成“有改动”。
7. 作为审查者，我希望没有活跃会话的项目仍可浏览文件和 Git 历史，以便不必为了看代码而运行 Agent。
8. 作为终端用户，我希望一条 pi 命令打开或唤回审查台并选中当前项目与会话，以便减少手工定位。

### 布局与文件导航

9. 作为审查者，我希望项目、文件、内容和回复处于固定顺序，以便形成稳定的操作习惯。
10. 作为审查者，我希望折叠不需要的栏，以便专注阅读回复或 diff。
11. 作为审查者，我希望折叠后仍能看到恢复入口和相关计数，以便不会丢失所在位置。
12. 作为审查者，我希望随时展开文件树，以便查看没有发生改动的上下文文件。
13. 作为审查者，我希望目录按需加载，以便大项目不会在打开时被完整扫描。
14. 作为审查者，我希望从改动文件跳到完整文件，以便不局限于 diff 的局部上下文。
15. 作为审查者，我希望点击回复中的明确文件路径定位到对应文件，以便把说明与代码直接对上。
16. 作为审查者，我希望带有行号的文件链接尽可能定位到相应行，以便快速查看具体位置。

### 本轮报告

17. 作为审查者，我希望看到 Agent 这一轮捕获到的净改动，以便不把仓库中已有的未提交改动算进本轮。
18. 作为审查者，我希望本轮报告和回复同步切换轮次，以便不会把旧解释与新改动配在一起。
19. 作为审查者，我希望保留现有 unified、split、词级差异和改动跳转，以便不用重新适应退化后的 diff 阅读器。
20. 作为审查者，我希望知道某轮没有报告还是报告不可用，以便不会把缺失误认为没有改动。
21. 作为审查者，我希望中断、失败和不完整报告有明确提示，以便知道哪些结论不能依赖。
22. 作为审查者，我希望浏览旧轮次时新结果不会打断阅读，以便保留当前阅读位置。

### Git 历史

23. 作为审查者，我希望在“历史”页签浏览提交记录，以便了解代码过去如何演变。
24. 作为审查者，我希望查看某次提交涉及的文件及 diff，以便审查已提交的改动。
25. 作为审查者，我希望打开该提交版本的完整文件，以便查看当时的上下文而不是当前磁盘内容。
26. 作为审查者，我希望从历史文件明确切到当前文件，以便知道自己开始查看或编辑的是哪个版本。
27. 作为审查者，我希望查看分支引用和 blame，以便理解某段代码的来源。
28. 作为审查者，我希望 Git 不可用或目录不是仓库时仍能使用其他功能，以便 Git 不成为审查台的前提。

### 编辑

29. 作为主要只读的用户，我希望代码默认只读，主动按 `e` 后才能编辑，以便避免误改。
30. 作为经常修改 Markdown 的用户，我希望当前磁盘上的 Markdown 默认可编辑，以便直接修改文档。
31. 作为编辑者，我希望手动保存并支持 `Cmd+S`，以便由自己决定写入时机。
32. 作为编辑者，我希望清楚看到未保存状态，以便不会以为内存中的修改已经写入磁盘。
33. 作为编辑者，我希望切换文件或项目时不会静默丢失未保存内容，以便保留自己的工作。
34. 作为与 Agent 同时工作的编辑者，我希望保存前发现文件已被其他人修改，以便不会不知情地覆盖新内容。
35. 作为历史审查者，我希望历史文件和 diff 保持只读，以便不会把历史视图当成当前工作文件。

### 回复阅读与继续交互

36. 作为回复阅读者，我希望保留现有 Markdown、公式、Mermaid、函数图和代码高亮，以便回复的表达能力不退化。
37. 作为回复阅读者，我希望保留上一条、下一条、历史列表及回到最新回复，以便翻阅同一会话的回答。
38. 作为回复阅读者，我希望图表仍能缩放和拖动，以便读清复杂内容。
39. 作为回复阅读者，我希望保留源码查看与临时修改预览，以便检查或调整渲染效果，而不修改原始会话。
40. 作为回复阅读者，我希望粘贴 Markdown 即可临时预览，以便继续使用现有便利功能。
41. 作为回复阅读者，我希望深浅主题作用于整个窗口，同时保留回复的文档式排版，以便整体一致但不牺牲阅读体验。
42. 作为用户，我希望向当前活跃会话发送纯文本，以便阅读后直接继续讨论。
43. 作为用户，我希望发送时能分辨忙碌、离线、失败和已确认，以便不会误发或重复提交。
44. 作为中文用户，我希望输入法确认候选字时不会发送消息，以便可靠输入。

### 资源、运行与迁移

45. 作为长期使用者，我希望增加项目不会增加同等数量的页面和渲染器，以便资源占用不随项目数明显线性增长。
46. 作为长期使用者，我希望只有前台活跃项目监听文件，以便后台项目不会持续占用 CPU。
47. 作为长期使用者，我希望窗口回到前台时重新核对文件状态，以便既省资源又不显示过期内容。
48. 作为现有插件用户，我希望迁移期间有可用退路且不重复捕获，以便日常工具不会被试验版本破坏。
49. 作为现有插件用户，我希望最终只用审查台提供改动和回复能力，以便不维护重复入口。
50. 作为本机用户，我希望网页只能访问已授权项目及会话，以便本地服务不会变成任意文件读写入口。

## Implementation Decisions

### 1. 第一版交付边界

第一版包含四栏布局、项目管理、文件树、完整文件查看与编辑、本轮快照报告、Git 历史、回复能力迁入、本地服务、会话上报及 TUI 唤出命令。

Git 历史包括 log、提交 diff、历史文件、分支引用浏览及 blame。Git 操作为只读，不执行 checkout 或其他工作区变更。

实现可以分阶段验证，但阶段划分不意味着把编辑或 Git 历史移出第一版交付范围。

### 2. 独立插件与最终归属

新插件独立拥有捕获、报告、回复、布局和服务能力，不以运行旧插件为前提，也不长期依赖旧插件输出的 HTML 或内部数据接口。

复用现有 diff 算法、快照实现及回复渲染源码；不重新设计这些已经可用的能力。运行所需代码与资产随新插件交付，避免依赖用户机器上的旧插件安装目录。

最终 compact-tool 只保留 TUI 工具展示，移除其改动捕获、报告保存、页面及入口；visual-reply 的能力被完整接管后停用。旧入口的替代入口必须随迁移提供。

开发验证期间保留旧版本作为退路，但同一 pi 会话内只能有一个捕获者。启用新插件捕获前必须明确停用旧捕获；不能以两套同时采集作为过渡方案。具体切换机制在实现前核验，不预设现有插件已经有独立开关。

迁移删除、用户配置切换和所有现有会话的加载操作，应在新插件验证及用户确认后执行；写规格不授权立即执行这些操作。

### 3. 项目、会话、轮次与 Git 提交

- 项目：用户维护的本地目录，不是进程。
- 会话：由 pi 上报身份和状态；一个项目允许零到多个会话。
- 轮次：一次实际工作从开始到最终稳定结束的审查单位，不是每次模型内部工具往返。
- 本轮报告：现有快照机制为该轮捕获的净改动。
- 回复：对应轮次的最终答复；没有最终答复时明确显示缺失或失败。
- Git 提交：仓库历史对象，独立于会话和轮次。

为报告和回复记录稳定的会话及轮次关联，不能只用时间相近或“项目最新一份”猜测对应关系。同一项目的多个会话不能覆盖彼此的结果。

选择轮次时报告与回复同步切换。没有报告时展示原因，不回退显示其他轮次的报告。保留该轮原有用户提示作为理解报告的上下文。

切到 Git 历史不会把提交绑定到右栏回复；右栏保留已选轮次，并明确两者是不同来源。

### 4. 两类 diff 严格分离

“本轮”页签使用现有 compact-tool 快照机制，不引入 Git 基线。

沿用现有捕获范围和限制：Edit、Write、apply_patch；单文件快照上限 1 MiB，每轮原文预算 16 MiB；保留二进制、不可读取、中断及补丁失败等现有提示。命令、脚本、外部编辑等未追踪写入不扩展到本次范围。

“历史”页签读取 Git 提交。提交 diff 使用该提交与父版本的内容；根提交按空树处理。合并提交需明确所选父版本，默认第一父版本，不能显示一个没有说明比较来源的 diff。

沿用现有 diff 阅读能力，包括 unified/split、词级差异、换行及改动块导航。快照报告一经生成不因之后的手动保存或新一轮运行而改变。

捕获失败或报告不存在不等价于“确认仓库没有变化”。界面明确展示报告覆盖范围，不将未追踪写入宣称为已记录。

### 5. 布局与视觉依据

以 Paper 中“四栏审查、专注回复、专注改动、Git 历史”四张主画板为布局参考：

- 顺序为项目、文件、内容、回复，回复固定在最右。
- 项目栏默认约 176px，文件栏约 236px；内容与回复分享剩余空间。
- 内容栏顶部提供“本轮 / 历史”，不另开一个 Git 工作窗口。
- 文件栏同时承载相关改动文件列表与项目文件树。
- 各栏可折叠；收起后保留约 40px 窄条、恢复入口和有定义的计数。
- 内嵌的旧 diff 文件侧栏默认收起，避免重复导航。
- 所有面板属于同一页面和键盘体系，不使用 iframe。

第一版不追求像素级复刻。配色和装饰可后调，不因视觉重设计阻碍功能交付。

回复栏沿用现有 visual-reply 的真实文档排版，包括衬线正文、图表和源码样式；将样式限制在容器内，避免污染其他栏。主题由整个应用统一管理。

### 6. 文件导航与编辑语义

目录按需加载。代码视图使用 CodeMirror 6；视口虚拟化不等价于完整大文件加载没有成本，需要同时限制读取和缓存规模。

当前磁盘文件：Markdown 默认可编辑，代码默认只读，按 `e` 进入编辑。保存必须由用户主动触发，支持 `Cmd+S`，不自动保存。

保存前核对磁盘文件是否仍是打开时的版本。发生外部变化时保留用户草稿，阻止静默覆盖，提供重新载入或明确确认覆盖的操作；不做自动合并。切换文件、项目或关闭页面前应保护未保存内容，不能为了只保留一个编辑器实例而静默丢弃草稿。

Git 历史文件默认读取所选提交的完整内容且只读，提供明确的“打开当前文件”动作。diff 本身不作为可编辑文档。

回复源码编辑仍是临时渲染预览，不回写 pi 会话；它与保存磁盘 Markdown 文件是两种操作。

文件链接优先匹配当前报告中的完整路径并定位；不在报告但属于已授权项目的文件，打开完整文件。避免仅凭同名文件猜测目标。无法解析、越界或文件不存在时明确反馈，不静默跳到错误文件。

### 7. 回复能力按现有实现迁入

保留现有 Markdown 扩展、公式、Mermaid、函数图、代码高亮及复制、图表缩放拖动、回复翻页、历史列表、阅读位置恢复、查看源码、临时源码修改和粘贴预览。

原始回复以 pi 会话为事实来源，保存引用和必要的导航元数据，不另建一套完整对话存档。已有“仅收到或打开过的回复进入预览历史”等边界沿用现有实现，不扩展成全会话扫描。

新轮次到达时，正在查看旧内容的用户不被强制跳转；提供返回最新轮次的入口。所有自动跟随仍需保持回复与本轮报告一致。

深浅主题统一作用于整窗。不增加自定义配色系统或各栏独立主题；原有额外纸色偏好不要求扩展到整个应用。

粘贴预览不增加草稿库或多份文档管理。

### 8. 向活会话发消息

沿用现有 visual-reply 的纯文本输入及活会话桥接，不另起 Agent，不直接修改会话文件。

消息继续目标会话的当前上下文；阅读旧轮次不意味着回到旧上下文或新建分支。多会话项目中必须明确发送目标。

保留忙碌拒绝、断线状态、输入法保护、发送确认和失败保留草稿行为，不自动重试不确定的提交。不扩展附件、流式回显、排队发送或斜杠命令补全。

权限对话框、工具执行过程及会话管理仍留在 pi 终端。

### 9. 服务与技术边界

TypeScript、Node 内置 HTTP、原生 DOM 和 esbuild；复用现有 jsdiff 与回复渲染栈。第一版不引入前端框架或 Electron。

本地服务由各会话共享，页面不各自启动一个后端。pi 侧扩展负责捕获及状态上报，服务负责目录和文件访问、Git 查询、结果索引与前端分发；服务不接管 Agent 运行。

逻辑接口至少覆盖：

- 项目列表及维护。
- 会话身份、工作状态、断开和轮次索引。
- 目录懒加载、当前文件读取及手动保存。
- 报告与回复按项目、会话、轮次读取。
- Git log、提交文件与 diff、历史文件、分支引用及 blame。
- 事件订阅、活会话消息发送及 TUI 唤出定位。

具体路由命名不在本规格锁死。选择推送方式时参考现有共享服务，避免每项目一个长连接导致浏览器连接资源耗尽。

只监听数字 loopback 地址，复用现有 Host、Origin、Bearer token 和签名会话引用的守卫。新增通用文件读写能力必须限制在授权项目根内，处理路径穿越和符号链接越界；不能仅复制原有会话读取守卫就宣称新文件接口已安全。

### 10. 状态与资源约束

工作状态来自 pi 扩展主动上报，不扫进程、不用文件变化猜测 Agent 是否工作。已有会话需要实际加载扩展后才能上报；全局安装不会自动让已运行会话加载新代码。

项目行左侧状态表示是否有会话正在工作；右侧数量表示当前选定本轮报告的改动文件数，不把它冒充未读轮次数。多会话项目显示范围必须清楚；完整跨项目未读模型不在本次范围。

只监听前台活跃项目，忽略依赖目录、Git 内部目录及构建产物，去抖约 200ms。失去前台或页面关闭时停掉文件监听，回到前台时核对当前视图。后台 pi 的必要捕获和结果上报继续运行，否则下一次打开就无法审查。

项目列表主要保留元数据；不为每个项目常驻文件树、完整文件、回复图表和 diff 渲染实例。切换时释放不再使用的渲染资源，同时保护未保存内容。

### 11. 无报告、失败与恢复

区分无净改动、未捕获、尚未加载扩展、捕获失败、不完整、回复缺失、会话离线、文件不存在、历史不可用等用户可见状态。

复用现有错误与边界提示，不为未知状态伪造成功。一次文件读取、图表渲染或 Git 查询失败，不应让其他项目及整个页面不可用。

服务重启或页面重连后，以持久报告和原始会话引用重新建立可审查状态；不只依赖连接期间的一次性通知。具体保留策略在沿用现有会话和报告能力的范围内实现，不增加通用归档系统。

## Testing Decisions

### 测试边界

优先使用两个高层边界，而不是为每个面板另造测试接口：

1. **本地服务的公开行为**：用真实临时目录、Git 仓库、会话样本和报告驱动服务，验证请求结果及实际磁盘内容。pi 事件在扩展边界输入，不 mock 全部底层文件函数。
2. **浏览器中的真实审查流程**：连接隔离服务和确定性会话驱动，验证跨项目、跨轮次、跨面板及输入保存行为，不产生付费模型调用。

对捕获与轮次关联，可补一个通过真实 pi 扩展加载器运行的集成检查，以验证事件时序和工具写入挂钩。复用现有测试驱动，不额外引入应用层依赖注入系统。

### 核心检查

- 至少三个项目正确切换；同一项目两个会话、各两轮的报告与回复不串线。
- 本轮快照与 Git 提交 diff 使用不同基线；存在预先未提交改动时不会误计入本轮。
- 无报告、空净改动、捕获失败和中断状态可区分。
- 工具写入前捕获原文；Edit、Write、apply_patch 及已有容量限制保持现有行为。
- 目录懒加载、项目根限制、符号链接越界及文件访问失败有真实文件系统验证。
- Markdown 编辑、代码只读切换、手动保存及保存后实际内容正确。
- 外部修改导致保存冲突时，磁盘不被静默覆盖、草稿不丢失。
- 切换项目或文件时未保存内容得到保护。
- 历史文件是提交版本而非当前磁盘内容；根提交、合并提交比较来源明确。
- 回复文件链接能定位改动或打开完整文件，不混淆同名路径。
- 旧轮次阅读不被新结果打断，回到最新后两栏重新配对。
- 公式、Mermaid、函数图、缩放、源码临时修改、粘贴、翻页及深浅主题无关键退化。
- 活会话发送、忙碌拒绝、离线、输入法确认和不确定提交保留草稿行为正确。
- 服务拒绝错误 Host、跨来源及未认证写入请求，前端不获得任意文件访问权。
- 失去前台或关闭页面后停止文件监听，回到前台核对状态；Agent 捕获不受页面关闭影响。
- 迁移后同一会话仅有一个捕获者，新的 TUI 入口存在，工具展示仍可用。

测试只断言用户能观察到的行为，不锁定 DOM 私有结构、内部缓存形式或函数调用次数。快照和渲染的已有测试优先迁入，不重复实现被测算法来计算期望值。

### 现有测试经验

compact-tool 已有改动捕获、补丁解析、diff 页面及真实加载相关检查。visual-reply 已有隔离服务、签名回复、活会话输入、浏览器历史、主题、图表和多连接回归，以及无需真实模型调用的 pi 驱动。

新仓库尚无实现与测试配置，应复用这两者的有效验证方式，而不是把旧 GUI 宿主草案的测试框架要求照搬进来。

### 性能验收

使用隔离浏览器及服务，记录宿主、测量口径、项目数、选中内容规模和重复切换前后的结果。分别报告页面与服务占用，不把 JavaScript heap 当成应用全部内存，也不把已有浏览器共享开销算成每个项目的独立成本。

交接中的空闲 CPU 接近零、内存小于 150MB 为目标，尚无实测基线。默认以隔离浏览器的页面任务内存检查 150MB 目标，另报服务 RSS 与浏览器整体开销，不宣称这等于应用全部内存。至少比较 3 个与 15 个项目，以及重复切换后的资源趋势，验证没有按项目数常驻完整内容，也没有明显累积泄漏。

大文件验证同时检查读取量与渲染，不只检查滚动是否流畅。自动测试优先使用隔离、无头环境；涉及用户桌面焦点的实际唤出测试，执行前说明影响并获得许可。

- 图片和二进制的专用查看编辑器。
- 附件、流式聊天、消息队列、斜杠命令补全及会话分支管理。
