# 性能优化记录

开发、测试和桌面更新流程仍以 [development.md](development.md) 为准。本文件保存长期测量口径、已验证收益和后续调查入口，不依赖聊天或旧临时目录。

## 当前优先级

2026-11-01 用户明确：**主界面的文件编辑器和 Diff 优先；pi 集成与独立 Markdown 编辑窗口不优先。** 后两项仅保留已完成的摸排与探针，不继续实现。后续选题按这一优先级排序。

## 工作方式

1. 先选真实操作链路，建立可重复夹具与优化前基线。
2. 优先减少无关读取、重复计算和 DOM 重建，不用删功能、截断内容或跳过保护换速度。
3. 用功能断言保护关键行为；耗时用于同机对照，不设未经验证的通用时间上限。
4. 每批结束保存数据摘要、测试边界、任务状态与未解决问题。规格和独立任务见 [本地票据](../.scratch/performance/spec.md)。

```sh
npm run build
npm run test:performance
```

脚本直接打包当前源码中的渲染器，在隔离 Chrome 中检查块复用、引用、脚注、图表、图片和主题，同时采样公共工作区接口。结果在 `test-results/performance/after.json`，截图在同目录的 `render.png`。

采集一批优化前的数据使用 `npm run test:performance -- --baseline`，输出为 `baseline.json`。该参数只选择文件名，不切换实现、不放宽断言。已存在的重复工作可能使断言失败，但测量仍在 `finally` 中保存。对照采样时不要同时跑其他测试。

原生验证使用 `npm run test:desktop`。它会打开独立测试应用并使用真实系统菜单、按键和对话框；须先获得桌面操作许可。结果在 `test-results/desktop/result.json`。

原始结果是可重建的产物，不提交；每批的摘要与限制保存在本文件，避免后续运行覆盖历史结论。

## 2026-11-01：第一批

基线提交：`23d5d136d3fd51e8aa84df4f1644e724d0a0627b`。环境：macOS arm64、Node v24.20.0、Chrome 156.0.8078.79。用户授权占用桌面测试。本批没有模型调用、真实 Agent 输入、旧插件迁移或日用项目文件写入。

### 已确认原因和实现

- `web-src/reply.js` 原先每次销毁整篇预览，重新高亮代码、解析 HTML、挂载图表和读取相对图片。现在仍全局解析 Markdown，以保持引用和脚注语义；按平衡的顶层 token 分组，保留相同前缀、后缀的 DOM 和挂载资源，只替换变化区间。代码高亮缓存只保留当前文档用到的内容，不跨文档无限增长。
- 阅读摘要不再深克隆整篇 DOM；图表回调的摘要更新合并到微任务。改变主题、纸色、字体或图表内容仍刷新相应内容；移除块会销毁图表资源。
- `web-src/app.js` 的文件源码模式原先仍会在编辑后计算隐藏预览。现在不安排该工作，切回分栏或预览时读取最新草稿。保留原有 150ms 防抖，没有用缩短等待掩盖计算成本。
- `src/git.ts` 的 `workspace-file` 原先计算完整工作区，连无关的未跟踪文件也逐个读取和构建 Diff。现在只查所选分组，只读取目标需要的文本。工作区概览仍计算全部原有范围内的文件，完整 Diff、staged/unstaged 比较和读取边界不变。

- 没有 WKWebView 的优化前同口径数据，因此不把 Chrome 的倍数直接当成桌面倍数。没有测量本批的应用总物理内存、长期泄漏或所有大型日用项目。

## 2026-11-01：第二批，主界面编辑器与 Diff

第一批已提交为 `1961c13`，本批以该提交的主编辑器与 Diff 为基线。没有修改 pi 状态协议或独立 Markdown 窗口的轮询实现。

### 实现与对照

- `web-src/editor.js` 原先在每次输入的状态更新中调用三次 `sliceDoc()`，只为判断是否存在未保存内容。改用 CodeMirror 原生 `Text.eq` 比较当前文本与已保存文本结构；仅保存或明确需要全文时序列化。`markSaved` 用当前行分隔规则构建已保存文本，保留 CRLF、保存过程中继续输入、完全撤销和手动恢复原内容的语义。
- `web-src/diff.js` 原先为每个高亮边界从头查找 token/词级范围，长行出现重复扫描。现在沿有序范围单向前进；同一 Diff 挂载中的行配对与高亮结果缓存供两种布局共用，临时 token 缓存渲染后清空。缓存不跨文件常驻，不截断内容，不改变折叠或文件展开方式。

同一隔离 Chrome、相同依赖环境，输入各三次取中位数；Diff 各场景记录一次冷渲染和两次布局切换，不冒充生产百分位数：

| 场景 | 优化前 → 后 |
| --- | ---: |
| 1,741,780 字节文件，每次输入的全文转换 | 3 次 → 0 次 |
| 同文件，语法树就绪后的同步输入更新 | 5.6 → 4.6 ms |
| 同文件，刚跳到末尾时的同步输入更新 | 23.2 → 21.4 ms |
| 137,797 字节单行 Diff，首次同步渲染 | 337.5 → 102.0 ms |
| 同行，Unified → Split 同步渲染 | 182.3 → 17.1 ms |
| 同行，Split → Unified 同步渲染 | 171.8 → 16.8 ms |
| 1,000 行修改，布局切换的词级比较次数 | 每次 1,000 次 → 0 次 |

全文转换计数来自对真实 `EditorState.sliceDoc` 的透明计数：大文件原先每键请求构造约 522 万个全文字符，优化后为零；这不是应用物理内存测量。小文件未见稳定时延改善。1,000 行普通 Diff 的首次渲染也没有明显改善；本批主要改善长行和重复切换，不据此宣称所有 Diff 同比提速。

冷态输入仍有约 20ms 同步成本。CPU profile 的热点在 CodeMirror/Lezer 解析，依赖实现中的事务解析预算为 `Work.Apply` 20ms。本批没有禁用语法高亮、篡改第三方预算或隐藏该成本。`openMs` 包含 Playwright 等待，不作为软件打开延迟指标。

复现入口：

```sh
npm run build
npm run test:main-performance -- --ref=1961c13 --baseline
npm run test:main-performance
# 按需获取冷态输入的解析 CPU profile：
npm run test:main-performance -- --profile
```

`--ref` 仅从指定 Git 提交读取 `web-src/editor.js` 和 `web-src/diff.js`，其余模块和依赖仍来自当前目录；不是完整重建历史发布包。基线在“输入不应转换全文”的断言处预期失败，测量仍会保存。产物为 `main-editor-before.json`、`main-editor-after.json`、`main-diff.png`；可选 profile 为 `main-editor.cpuprofile`，均在 `test-results/performance/`。

### 验证

- 通过：`check`、`test:main-performance`、`test:editor`、`test:diff`、`test:e2e`、`test:polish`、`test:redesign`、`test:files`、`test:performance`、`verify:package`、`test:desktop`。

## 2026-11-01：第三批，长 Diff 滚动绘制

用户反馈第三栏长 Git Diff 往返滚动时像分片重新出现，滚动不跟手。不能根据这种观感直接认定为应用懒加载。

### 复现与根因

隔离 Git 仓库中的 2,500 行 TypeScript 全部修改，真实工作区第三栏显示 5,000 行 Unified Diff、45,000 个语法高亮 token。每轮用相同脚本向下、向上各滚动约 6,000px，页面不发生文件修改。

- Chrome 往返过程中没有 Git 接口请求、内容节点增删或文本变化，布局次数也为零。源码没有这条滚动路径的懒加载或虚拟列表；排除本夹具中反复获取/计算内容的解释。
- 真实 WKWebView 严重落后于系统滚轮输入。单变量 A/B/A：保留 token 的 `opacity: .92` 时严重卡顿；仅取消透明度后恢复稳定调度；改回透明度后再次卡顿。改表格的 `border-collapse` 没有解决问题。
- 根因在 `web-src/style.css` 的逐 token 透明度。它为大量碎片文字引入透明度绘制分组，放大 WebKit 的长表格绘制成本。本次只删除这条规则，保留所有高亮节点和颜色分类、全文、折叠与滚动结构，没有增加另一套懒加载或虚拟列表。

### 同口径结果

真实 macOS 15.7.9 / WKWebView、同一系统像素滚轮脚本，两轮采样。旧代码帧样本很少，因为页面已经跟不上；以下为放大的合成负载，不是生产百分位数：

| 指标 | 优化前，两轮 | 优化后，两轮 |
| --- | --- | --- |
| 每轮约 5–6 秒内的 rAF 回调数 | 10 / 10 | 302 / 293 |
| 帧间隔中位数 | 659 / 768 ms | 17 / 17 ms |
| 超过 25ms 的已采样帧间隔 | 10 / 10 | 0 / 0 |
| 往返输入后的滚动位置 | 仍留在下方 | 均回到顶部 |
| 内容增删 / 文本变化 | 0 / 0 | 0 / 0 |

Chrome 的两轮帧间隔 p95 从 33.3 / 33.3ms 降到 16.8 / 16.7ms，完整高亮 token 数仍为 45,000。Chrome 和 WKWebView 分开报告；没有把 rAF 采样当成屏幕实际呈现 FPS，也没有据此宣称已达到显示器的 120Hz。CGEvent 输入经过系统事件链，但不是手指触控板实测。

### 回归与复现

```sh
npm run check
npm run test:diff-scroll
npm run test:diff-scroll-native
# 只叠加旧共享样式，预期回归断言失败：
```

浏览器断言完整高亮不会为每个 token 建立透明度分组，往返滚动不请求 Git、不替换内容。原生回归还检查真实滚动到远处再回到顶部、原节点保留，以及调度不再持续落后于静态页面；WebKit 的异步滚动可能不向 JavaScript 转发 `wheel`，所以不以该事件数量判断滚动是否生效。
